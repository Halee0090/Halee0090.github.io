02프로젝트 개요

    

      
문제해결

      
        
팀원마다 서버를 수동 설정하다 항목이 빠져 오류 반복Shell Script로 초기 설정 표준화

        
학교 네트워크를 바꿀 수 없어 외부 접속 경로가 없음Cloudflare Tunnel로 포트 개방 없이 외부 공개

        
코드 변경이 잦아 빌드·배포를 수동으로 반복Jenkins + GitHub Webhook으로 자동 배포

        
Jenkins 관리자 화면이 외부에 노출됨Cloudflare Access로 공인 IP·GitHub 계정 기준 접근 제한

      
    


    
03주요 작업

    
    
      
  1. 1개발·운영 서버 인프라 구축 및 초기 설정 자동화
    학교 서버 WSL(Ubuntu 24.04) 환경에 SSH, 사용자·권한, 호스트명, 시간대, UFW, Docker를 설정하고, 팀원들이 같은 환경으로 작업할 수 있도록 Shell Script로 정리해 초기 설정을 자동화했습니다.
    2. 
      
  2. 2Cloudflare Tunnel로 개발·운영 서비스 외부 연결
    가비아에서 구입한 도메인을 Cloudflare Tunnel에 연결해 개발·운영 도메인을 각 서버의 서비스로 연결했습니다.
    3. 
      
  3. 3Jenkins 활용하여 CI/CD 파이프라인 구축
    GitHub에 코드를 push하면 Webhook이 작동해 코드를 통합·테스트하고, Docker 이미지를 빌드해 배포한 뒤 헬스 체크까지 마치면 Slack으로 알림이 오도록 구성했습니다.
    
        
    4. 
      
  4. 4Jenkins 접근 보안 적용
    외부에서 접속할 수 있던 Jenkins 관리자 페이지에 보안을 설정했습니다. Cloudflare에서 공인 IP와 GitHub Webhook 경로의 IP만 허용하고, GitHub ID 화이트리스트로 팀원만 접근하도록 해 보안을 강화했습니다.
    5. 
    


    
04트러블슈팅

    

      DB 데이터 유실 및 복구 문제
      

        
문제
재배포 후 앱은 열렸지만 기존 사용자·정책 데이터가 조회되지 않음

        
원인
GitHub 프로젝트 폴더가 바뀌면서 재배포 시 새 볼륨이 생성되었고, 앱이 기존 볼륨이 아닌 새 볼륨에 연결되어 있었음

        
조치
docker volume ls로 기존 볼륨을 찾아 pg_dump로 백업하여 현재 DB에 복원

        
결과
테이블 20개, 정책 데이터 23건, 사용자 데이터 10건 복구 확인, 웹 서비스에 데이터가 잘 반영됨

      

    

    

      Cloudflare Access 적용 후 GitHub Webhook에 302 응답이 발생한 문제
      

        
문제
Jenkins 관리자 페이지가 외부에 공개되어 있어 Cloudflare Access로 Jenkins 전체 접근을 공인 IP 기준으로 제한했더니, push해도 자동 빌드가 시작되지 않았고 Webhook Recent Deliveries에 302 Found 반복

        
원인
Jenkins 전체 경로에 적용한 IP 제한 때문에 학교 IP가 아닌 GitHub의 Webhook 요청도 Access 인증 단계로 보내져 /github-webhook/ 경로까지 전달되지 않음

        
조치
관리자 화면 접근 제한은 유지하고, /github-webhook/ 경로 전용 Access Application을 만들어 GitHub 공식 hooks IP 대역에만 Bypass 정책 적용

        
결과
Delivery를 재전송해보았더니 200 OK로 응답하고, push 시 자동 빌드·배포가 다시 동작함을 확인 (관리자 화면은 여전히 IP 제한 유지)

      

    


    
05배운 점

    
팀원마다 서버를 따로 설정하자 같은 오류가 반복됐습니다. 설정을 Shell Script로 코드화한 뒤부터는 누가 실행해도 같은 환경이 만들어졌고, 인프라는 한 번 구축하는 것보다 같은 상태를 다시 만들 수 있게 하는 것이 중요하다는 걸 배웠습니다.

    
또한 Jenkins 관리자 페이지에 IP 제한을 걸었을 때 GitHub Webhook 요청까지 막혀 자동 빌드가 멈춘 일을 겪으며, 보안 설정을 바꾸면 연관되어 있는 것들도 함께 확인해야 한다는 것을 배웠습니다. 관리자 접속과 자동화 요청은 목적과 출발지가 다르기 때문에 접근 정책도 경로별로 나눠야 했습니다.

    
팀장으로 프로젝트를 주도하면서 개발, CI/CD, 보안 담당자가 서로 어떤 설정에 의존하는지 파악하고, 각 작업이 끊기지 않도록 순서를 조율하는 것이 중요하다는 것을 느꼈습니다.

배경
공격 경로를 재현하고 검증하려면 팀 전체가 사용할 EKS 환경이 먼저 필요했습니다. AWS 콘솔에서 인프라를 구성해보고, 그 구성을 그대로 Terraform 코드로 작성하여 구성해보았습니다.

      
목적
① 수업에서 배운 IaC를 VPC·IAM·EKS 실제 환경에 적용 ② Terraform 모듈 단위로 설계하여 충돌 없이 분업

    


    
03주요 작업

    
    
      
  1. 1Terraform 모듈 구조 설계

    2. 
      
  2. 2EKS Cluster 구성
    IAM 모듈에서 만든 Cluster Role을 연결하고, 두 AZ의 Public·Private Subnet 4개에 클러스터를 구성했습니다. 인증 모드는 EKS API로 설정했습니다.
    3. 
      
  3. 3Worker Node 구성 (Managed Node Group)

  4. 4Add-on 설치 순서 제어

    5. 
      
  5. 5배포 검증
    fmt → validate → plan → apply 후 콘솔에서 VPC, IAM, EKS가 차례대로 생성됐는지 확인하고, EKS 클러스터에 연결해 Node와 Pod를 확인하였습니다.

온프레미스 쿠버네티스 웹·DB 배포 및 운영

    
수업 종합 실습 · 2026.10 · Kubernetes(kubeadm) · Ingress(TLS) · ConfigMap · Secret · PVC · HPA · MySQL

    
  

  

    
01소개

    
웹과 주문 DB로 구성된 쇼핑몰 서비스를 온프레미스 쿠버네티스 클러스터에 배포하고, 배포 후 운영 작업(Day-2)까지 직접 수행한 실습입니다.

    

      
요구사항
① 웹 서버는 무중단 배포와 자동 확장 ② 주문 DB는 Pod가 재시작되어도 데이터 유지 ③ HTTPS로 서비스 공개

    


# 구성
[사용자] → Ingress (HTTPS · TLS Secret)
         → Service web-svc → Deployment web (nginx ×2, HPA 2~5)  ← ConfigMap
           Service db-svc  → Deployment db  (mysql ×1)           ← ConfigMap · Secret
                                    ↓
                             PVC db-pvc (StorageClass local-path, 동적 생성)


    
02주요 작업

    
    
      
  1. 1설정과 비밀 정보 분리
    DB 이름·사용자는 ConfigMap, DB 비밀번호와 TLS 인증서는 Secret으로 분리해 YAML에 평문으로 남기지 않음
    2. 
      
  2. 2DB 배포 (PVC + Recreate)
    동적 PVC(1Gi, RWO)를 /var/lib/mysql에 연결. RollingUpdate를 쓰면 새 Pod와 기존 Pod가 같은 데이터 폴더를 동시에 쓰게 되므로 Recreate 전략 적용
    3. 
      
  3. 3웹 배포 (무중단 업데이트 + 자동 확장)
    RollingUpdate(maxSurge 1, maxUnavailable 0)로 기존 Pod를 먼저 내리지 않도록 설정. requests/limits를 지정하고 CPU 50% 기준 HPA(2~5) 적용
    4. 
      
  4. 4HTTPS 공개
    자체 서명 인증서로 TLS Secret을 만들고, Ingress에서 도메인 → web-svc로 연결
    5.

04배운 점

    
PVC는 Pod 장애로부터 데이터를 지켜 주지만, 잘못된 명령까지 막아 주지는 못한다는 것을 테이블 삭제 사고를 재현하며 확인했습니다. 데이터 유지와 백업은 별개의 문제였습니다.

    
같은 Deployment라도 웹은 RollingUpdate, DB는 Recreate처럼 데이터를 다루는 방식에 따라 배포 전략을 다르게 골라야 한다는 것을 배웠습니다.
