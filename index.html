PROJECT 01

    
TravelHunter

    
5인 팀 (개발 1 · CI/CD 2 · 보안 2) · 2026.06 ~ 진행 중 · 프로젝트 주도 · 인프라 · CI/CD

    
  

  

    
01프로젝트 소개

    
국내 여행 정책·혜택을 찾아 여행 일정을 계획하는 서비스입니다. 저는 프로젝트를 주도하며 서버 인프라, 배포 자동화, 접근 보안을 맡았습니다.

    

      
      
      
    


    
02배경과 목적

    

      
배경
학교 PC를 서버로 쓰는 환경에서 팀원들이 각자 수동으로 설정하며 오류가 반복되었고, 학교 네트워크 설정은 바꿀 수 없어 외부에서 접속할 방법이 없었습니다.

      
목적
① 모든 서버에 같은 설정 적용 ② 포트 개방 없이 외부 접속 ③ 코드 변경 시 자동 배포 ④ 허가된 팀원만 관리자 화면 접근

    

    

    
03주요 작업

    
    
      
  1. 1서버 초기 설정 자동화 (Shell Script)
    실행 권한과 호스트명 조건을 확인한 뒤 사용자·권한, 패키지 업데이트, UFW, Docker 설치·활성화를 순서대로 수행하는 스크립트로 팀원 서버 환경을 통일
    2. 
      
  2. 2외부 접속 구성 (Cloudflare Tunnel)
    ngrok(사용량 제한 · 실행마다 URL 변경)과 비교해 인바운드 포트 개방 없이 고정 도메인을 쓰는 Cloudflare Tunnel을 선택, cloudflared로 개발·운영 도메인 2개 연결
    3. 
      
  3. 3Docker Compose 서비스 구성
    cloudflared · Caddy · frontend · backend · PostgreSQL · Jenkins 6개 컨테이너로 분리하고, Caddy가 /api는 backend로 분기. healthcheck로 db → backend → frontend 순서로 기동
    4. 
      
  4. 4Jenkins 배포 자동화 (Controller · Agent)
    개발 서버의 Controller에 개발·운영 Agent를 SSH로 연결. 체크아웃 → Compose 검증 → 이미지 빌드 → DB 마이그레이션 → 배포 → 헬스체크 → Slack 알림
    
        
    5. 
      
  5. 5관리자 접근 보안 (Cloudflare Access)
    GitHub 조직 멤버 인증, GitHub 계정 MFA, 학교 공인 IP 조건을 조합한 정책을 적용하고, 허용·차단 결과를 Access 로그와 대조
    6. 
    


    
04트러블슈팅

    

      재배포 후 DB 데이터가 사라진 것처럼 보인 문제
      

        
문제
재배포 후 앱은 열렸지만 기존 사용자·정책 데이터가 조회되지 않음

        
원인
프로젝트 폴더가 바뀌며 Compose가 새 이름의 빈 볼륨을 만들었고, 앱이 그 볼륨에 연결됨

        
조치
docker volume ls로 기존 볼륨을 찾아 임시 PostgreSQL 컨테이너에 연결하고 pg_dump로 추출해 복원

        
결과
테이블 20개, 정책 데이터 23건 복구. 백업 파일은 프로젝트 폴더 밖에 보관

      


$ docker volume ls | grep db
travelhunterapp_travelhunter-db        ← 기존 데이터가 있는 볼륨
travel-hunter-onprem_travelhunter-db   ← 앱이 연결된 새 빈 볼륨

    

    

      Cloudflare Access 적용 후 GitHub Webhook 302 응답
      

        
문제
IP 제한 적용 후 push해도 자동 빌드가 시작되지 않고 Webhook 기록에 302 Found 반복

        
원인
Jenkins 전체 경로에 건 IP 제한 때문에 Webhook 요청도 Access 인증 단계로 보내짐

        
조치
관리자 접근 제한은 유지하고, /github-webhook/ 전용 Access Application에 GitHub hooks IP 대역만 Bypass 적용 후 Delivery 재전송

        
결과
Webhook 2xx 응답, Jenkins 자동 빌드 정상 완료

      

    


    
05배운 점

    
증상과 원인을 나눠 봐야 한다는 것을 배웠습니다. "데이터 삭제"처럼 보인 장애는 볼륨 연결 문제였고, Webhook 장애는 Webhook 기록과 Access 로그를 대조하고 나서야 원인을 찾을 수 있었습니다.

    
처음 주도한 프로젝트에서, 서로 다른 업무를 맡은 팀원들의 작업 순서를 조율하고 작업마다 기록을 남기는 것이 꼭 필요하다는 것을 배웠습니다.

PROJECT 02

    
AWS EKS 인프라 IaC 구축 (Terraform)

    
3인 팀 · 2026.09 ~ 진행 중 (인프라 IaC 완료) · EKS 모듈 담당 · VPC/IAM 공동 · IRSA 모듈 분리

    
  

  

    
01프로젝트 소개

    
보안 검증 실습(CNAPP)에 쓸 AWS EKS 환경을 Terraform으로 구축했습니다. 저는 EKS Cluster·Node Group 모듈을 맡았고, VPC·IAM 모듈은 팀원과 함께 작성했습니다.

    

    
02배경과 목적

    

      
배경
수업에서 배운 IaC를 실제 인프라에 적용하고 싶었고, 프로젝트 후반에 Terraform 코드의 보안 취약점을 배포 전에 점검하는 단계가 있어 인프라가 코드로 존재해야 했습니다.

      
목적
① 수업에서 배운 IaC를 실제 EKS 환경에 적용 ② 배포 전 보안 점검 대상으로 만들기 ③ 3명이 모듈 단위로 충돌 없이 분업

    


    
03주요 작업

    
    
      
  1. 1Terraform 모듈 구조 설계
    VPC / IAM / IRSA / EKS 모듈로 나눠 environments/dev에서 output을 조합해 apply. Region·Subnet ID 하드코딩 없이 변수화, tfvars·tfstate는 저장소에서 제외
    2. 
      
  2. 2EKS Cluster 구성
    두 AZ의 Public·Private Subnet 4개 연결, 인증 모드 EKS API. API·Audit·Authenticator·Controller Manager·Scheduler 로그 5종을 CloudWatch로 수집
    3. 
      
  3. 3Worker Node 구성 (Managed Node Group)
    Private Subnet 2개에만 배치(t3.medium, 최소·기본 2 / 최대 10). Launch Template으로 루트 디스크 gp3 30GiB · EBS 암호화
    4. 
      
  4. 4Add-on 설치 순서 제어
    네트워크 플러그인 없이 노드가 뜨지 않도록 VPC CNI → Node Group → CoreDNS · kube-proxy 순으로 depends_on 설정
    5. 
      
  5. 5배포 검증
    fmt → validate → plan → apply 후 Cluster·Node Group·Add-on Active, Worker Node 2개 Ready · 서로 다른 AZ · Public IP 없음 확인
    6. 
    


    
04트러블슈팅

    

      IAM 모듈에 생성 시점이 다른 리소스가 섞여 의존성이 꼬인 문제
      

        
문제
IRSA 코드를 추가하자 IAM·EKS 모듈 의존성이 꼬여 적용 순서를 잡을 수 없었고, Load Balancer Controller 설치까지 막힘

        
원인
EKS 생성 "전"에 필요한 Role과 "후"에 만드는 OIDC·IRSA가 한 모듈에 섞였고, Decoy S3가 필요한 시나리오 IRSA 때문에 LBC도 적용할 수 없었음

        
조치
IAM 담당 팀원과 원인을 확인해 IAM / IRSA 모듈을 분리하고, IRSA는 용도별 3개로 분리

        
결과
terraform plan 통과, Decoy S3 준비와 관계없이 LBC Pod Running

      


# 분리 전
modules/iam   ← Cluster·Node Role + OIDC + IRSA(LBC·시나리오 A·B)
# 분리 후
modules/iam                ← EKS 생성 전 (Cluster·Node Role)
irsa/oidc-lbc-irsa         ← EKS 생성 후, 즉시 필요
irsa/scenario-a-irsa       ← Decoy S3 준비 후
irsa/scenario-b-irsa       ← Decoy S3 준비 후

    

    

      Worker Node EC2에 Name 태그가 붙지 않은 문제
      

        
문제
Node Group에 태그를 지정했지만 EC2 인스턴스 이름이 비어 있음

        
원인
Managed Node Group 태그는 EC2 인스턴스 Name 태그로 자동 전파되지 않음

        
조치
Launch Template의 tag_specifications로 지정하고, 콘솔 수정 없이 Terraform이 노드를 교체하도록 적용

        
결과
Name 태그 적용, 코드와 실제 상태 일치 유지

      

    


    
05배운 점

    
모듈은 기능뿐 아니라 "언제 생성되는지"와 "무엇에 의존하는지"를 기준으로 나눠야 한다는 것을 배웠습니다. 모듈 경계에서 생긴 문제는 담당 팀원과 함께 봐야 빠르게 원인을 찾을 수 있었습니다.

    
콘솔에서 고치면 코드와 실제 상태가 어긋난다는 것도 배웠습니다. 다음 단계로 이 클러스터에 모니터링을 붙여 장애 감지와 원인 확인까지 검증할 계획입니다.
