PROJECT 01

    
TravelHunter

    
5인 팀 (개발 1 · CI/CD 2 · 보안 2) · 2026.06 ~ 진행 중 · 프로젝트 주도 · 인프라 · CI/CD · CI/CD 보안
FastAPI · Shell Script · Docker · Jenkins · Cloudflare · PostgreSQL · GitHub · AI Tool (Claude, ChatGPT)

    
  

  

    
01프로젝트 소개

    
국내 여행 정책·혜택을 찾아 여행 일정을 계획하는 서비스입니다. 5명이 2026년 6월부터 함께 작업하고 있고, 저는 프로젝트를 주도하며 인프라 구축, CI/CD 배포 자동화, CI/CD 보안을 맡았습니다. 현재는 클라우드로 마이그레이션을 진행하고 있습니다.

    

      
      
      
      
    

    
    

    
02프로젝트 개요

    

      
문제해결

      
        
팀원마다 서버를 수동 설정하다 항목이 빠져 오류 반복Shell Script로 초기 설정 표준화

        
코드 변경이 잦아 빌드·배포를 수동으로 반복Jenkins + GitHub Webhook으로 자동 배포

        
학교 네트워크를 바꿀 수 없어 외부 접속 경로가 없음Cloudflare Tunnel로 포트 개방 없이 외부 공개

        
Jenkins 관리자 화면이 외부에 노출됨Cloudflare Access로 허가된 팀원만 접근

      
    

    
03주요 작업

    
    
      
  1. 1개발·운영 서버 인프라 구축
    학교 서버 WSL(Ubuntu 24.04) 환경에 SSH, 사용자·권한, 호스트명, 시간대, UFW, Docker를 설정하고 개발·운영 2개 환경의 역할 분리
    ✔ SSH 접속, 방화벽 상태, Docker 서비스와 테스트 컨테이너 실행
    2. 
      
  2. 2서버 초기 설정 자동화 (Shell Script)
    실행 권한과 호스트명 등 입력 조건을 확인한 뒤 사용자·권한, 패키지 업데이트, UFW, Docker 설치, 서비스 활성화를 순서대로 수행하는 스크립트 작성
    ✔ 스크립트 1개와 실행 후 확인 절차를 문서로 정리
    3. 
      
  3. 3학교 네트워크 제약 아래 외부 접속 구성 (Cloudflare Tunnel)
    교수님께 터널링 방식을 소개받아 기능을 조사하고 Cloudflare Tunnel 선택. 팀원이 도메인을 Cloudflare에 연결한 뒤, 개발·운영 도메인 2개를 Tunnel에 추가해 각 서버의 서비스로 연결
    ✔ 개발·운영 사이트 2개를 외부에서 접속
    4. 
      
  4. 4Jenkins 배포 자동화 (Controller · Agent)
    개발 서버에 Jenkins Controller를 두고 개발·운영 Agent를 SSH로 연결. 운영 파이프라인에 체크아웃 → Compose 설정 검증 → 이미지 빌드 → DB 마이그레이션 → 배포 → 내부·외부 헬스 체크 → Slack 알림 단계를 구성하고, 개발·운영 환경변수 분리
    ✔ 운영 Agent에서 작업 실행, 작업 브랜치에서 파이프라인 테스트
    
        
    5. 
      
  5. 5Jenkins 접근 보안 (Cloudflare Access)
    GitHub 조직 멤버 인증, GitHub 계정 MFA, 지정 IP 조건을 조합한 접근 정책 적용. 관리자 로그인과 GitHub Webhook 경로는 용도가 달라 정책 분리
    ✔ 허용·차단 환경의 접속 결과와 Access 로그 대조
    6. 
    


    
04트러블슈팅

    

      재배포 후 DB 데이터가 사라진 것처럼 보인 문제
      

        
문제
재배포 후 앱은 열렸지만 기존 사용자·정책 데이터가 조회되지 않음

        
원인
프로젝트 폴더가 바뀌며 Compose가 새 이름의 빈 볼륨을 만들었고, 앱이 기존 볼륨이 아닌 새 볼륨에 연결되어 있었음

        
조치
docker volume ls로 기존 볼륨을 찾아 임시 PostgreSQL 컨테이너에 연결하고 pg_dump로 추출해 현재 DB에 복원

        
결과
테이블 20개, 정책 데이터 23건 복구 확인. 백업 파일은 프로젝트 폴더 밖에 보관

      


$ docker volume ls | grep db
travelhunterapp_travelhunter-db        ← 기존 데이터가 있는 볼륨
travel-hunter-onprem_travelhunter-db   ← 앱이 연결된 새 빈 볼륨

    

    

      Cloudflare Access 적용 후 GitHub Webhook에 302 응답이 발생한 문제
      

        
문제
Jenkins 관리 화면에 IP 제한을 적용한 뒤 push해도 자동 빌드가 시작되지 않았고, Webhook Recent deliveries에 302 Found 반복

        
원인
Jenkins 전체 경로에 적용한 IP 제한 때문에 학교 IP가 아닌 GitHub의 Webhook 요청도 Access 인증 단계로 보내져 /github-webhook/ 경로까지 전달되지 않음

        
조치
관리자 화면 접근 제한은 유지하고, /github-webhook/ 경로 전용 Access Application을 만들어 GitHub 공식 hooks IP 대역에만 Bypass 정책 적용

        
결과
실패한 Delivery를 재전송해 응답 재확인. 후속으로 Webhook Secret 서명 검증과 hooks IP 대역 변경 점검 예정

      

    


    
05배운 점

    
서버 구축은 설치 명령을 실행하는 데서 끝나지 않았습니다. 스크립트로 같은 설정을 다시 적용할 수 있게 만들고 SSH·방화벽·Docker 동작을 확인해야 환경을 설명할 수 있었고, 이 경험은 Terraform으로 인프라를 코드화한 Project 02로 이어졌습니다.

    
Webhook 302 오류를 겪으며 관리자 접속과 자동화 요청은 목적과 출발지가 다르므로 접근 정책도 경로별로 나눠야 하고, GitHub Delivery 응답과 Jenkins 실행 결과를 함께 봐야 한다는 점을 배웠습니다.

    
프로젝트를 주도하며 개발·CI/CD·보안 담당자가 서로 어떤 설정에 의존하는지 파악했습니다. 도메인 연결은 팀원이, 이후 Tunnel 연결과 서버·배포 환경은 제가 맡아 작업이 끊기지 않도록 조율했습니다.

PROJECT 02

    
AWS 인프라 IaC 구축 (Terraform)

    
3인 팀 · 2026.09 ~ 진행 중 (인프라 IaC 완료) · EKS 모듈 담당 · VPC/IAM 공동 · IRSA 모듈 분리

    
  

  

    
01프로젝트 소개

    
보안 검증 실습(CNAPP)에 쓸 AWS EKS 환경을 Terraform으로 구축했습니다. 저는 EKS Cluster·Node Group 모듈을 맡았고, VPC·IAM 모듈은 팀원과 함께 작성했습니다.

    

    
02배경과 목적

    

      
배경
수업에서 배운 IaC를 실제 인프라에 적용하고 싶었고, 프로젝트 후반에 Terraform 코드의 보안 취약점을 배포 전에 점검하는 단계가 있어 인프라가 코드로 존재해야 했습니다.

      
목적
① 수업에서 배운 IaC를 실제 EKS 환경에 적용 ② 배포 전 보안 점검 대상으로 만들기 ③ 3명이 모듈 단위로 충돌 없이 분업

    


    
03주요 작업

    
    
      
  1. 1Terraform 모듈 구조 설계
    VPC / IAM / IRSA / EKS 모듈로 나눠 environments/dev에서 output을 조합해 apply. Region·Subnet ID 하드코딩 없이 변수화, tfvars·tfstate는 저장소에서 제외
    2. 
      
  2. 2EKS Cluster 구성
    두 AZ의 Public·Private Subnet 4개 연결, 인증 모드 EKS API. API·Audit·Authenticator·Controller Manager·Scheduler 로그 5종을 CloudWatch로 수집
    3. 
      
  3. 3Worker Node 구성 (Managed Node Group)
    Private Subnet 2개에만 배치(t3.medium, 최소·기본 2 / 최대 10). Launch Template으로 루트 디스크 gp3 30GiB · EBS 암호화
    4. 
      
  4. 4Add-on 설치 순서 제어
    네트워크 플러그인 없이 노드가 뜨지 않도록 VPC CNI → Node Group → CoreDNS · kube-proxy 순으로 depends_on 설정
    5. 
      
  5. 5배포 검증
    fmt → validate → plan → apply 후 Cluster·Node Group·Add-on Active, Worker Node 2개 Ready · 서로 다른 AZ · Public IP 없음 확인
    6. 
    


    
04트러블슈팅

    

      IAM 모듈에 생성 시점이 다른 리소스가 섞여 의존성이 꼬인 문제
      

        
문제
IRSA 코드를 추가하자 IAM·EKS 모듈 의존성이 꼬여 적용 순서를 잡을 수 없었고, Load Balancer Controller 설치까지 막힘

        
원인
EKS 생성 "전"에 필요한 Role과 "후"에 만드는 OIDC·IRSA가 한 모듈에 섞였고, Decoy S3가 필요한 시나리오 IRSA 때문에 LBC도 적용할 수 없었음

        
조치
IAM 담당 팀원과 원인을 확인해 IAM / IRSA 모듈을 분리하고, IRSA는 용도별 3개로 분리

        
결과
terraform plan 통과, Decoy S3 준비와 관계없이 LBC Pod Running

      


# 분리 전
modules/iam   ← Cluster·Node Role + OIDC + IRSA(LBC·시나리오 A·B)
# 분리 후
modules/iam                ← EKS 생성 전 (Cluster·Node Role)
irsa/oidc-lbc-irsa         ← EKS 생성 후, 즉시 필요
irsa/scenario-a-irsa       ← Decoy S3 준비 후
irsa/scenario-b-irsa       ← Decoy S3 준비 후

    

    

      Worker Node EC2에 Name 태그가 붙지 않은 문제
      

        
문제
Node Group에 태그를 지정했지만 EC2 인스턴스 이름이 비어 있음

        
원인
Managed Node Group 태그는 EC2 인스턴스 Name 태그로 자동 전파되지 않음

        
조치
Launch Template의 tag_specifications로 지정하고, 콘솔 수정 없이 Terraform이 노드를 교체하도록 적용

        
결과
Name 태그 적용, 코드와 실제 상태 일치 유지

온프레미스 쿠버네티스 웹·DB 배포 및 운영

    
수업 종합 실습 · 2026.10 · Kubernetes(kubeadm) · Ingress(TLS) · ConfigMap · Secret · PVC · HPA · MySQL

    
  

  

    
01소개

    
웹과 주문 DB로 구성된 쇼핑몰 서비스를 온프레미스 쿠버네티스 클러스터에 배포하고, 배포 후 운영 작업(Day-2)까지 직접 수행한 실습입니다.

    

      
요구사항
① 웹 서버는 무중단 배포와 자동 확장 ② 주문 DB는 Pod가 재시작되어도 데이터 유지 ③ HTTPS로 서비스 공개

    


# 구성
[사용자] → Ingress (HTTPS · TLS Secret)
         → Service web-svc → Deployment web (nginx ×2, HPA 2~5)  ← ConfigMap
           Service db-svc  → Deployment db  (mysql ×1)           ← ConfigMap · Secret
                                    ↓
                             PVC db-pvc (StorageClass local-path, 동적 생성)


    
02주요 작업

    
    
      
  1. 1설정과 비밀 정보 분리
    DB 이름·사용자는 ConfigMap, DB 비밀번호와 TLS 인증서는 Secret으로 분리해 YAML에 평문으로 남기지 않음
    2. 
      
  2. 2DB 배포 (PVC + Recreate)
    동적 PVC(1Gi, RWO)를 /var/lib/mysql에 연결. RollingUpdate를 쓰면 새 Pod와 기존 Pod가 같은 데이터 폴더를 동시에 쓰게 되므로 Recreate 전략 적용
    3. 
      
  3. 3웹 배포 (무중단 업데이트 + 자동 확장)
    RollingUpdate(maxSurge 1, maxUnavailable 0)로 기존 Pod를 먼저 내리지 않도록 설정. requests/limits를 지정하고 CPU 50% 기준 HPA(2~5) 적용
    4. 
      
  4. 4HTTPS 공개
    자체 서명 인증서로 TLS Secret을 만들고, Ingress에서 도메인 → web-svc로 연결
    5.

04배운 점

    
PVC는 Pod 장애로부터 데이터를 지켜 주지만, 잘못된 명령까지 막아 주지는 못한다는 것을 테이블 삭제 사고를 재현하며 확인했습니다. 데이터 유지와 백업은 별개의 문제였습니다.

    
같은 Deployment라도 웹은 RollingUpdate, DB는 Recreate처럼 데이터를 다루는 방식에 따라 배포 전략을 다르게 골라야 한다는 것을 배웠습니다.
